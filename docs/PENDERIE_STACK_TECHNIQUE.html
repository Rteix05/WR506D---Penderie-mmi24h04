La stack de Penderie, choix par choix

Penderie est une application mobile pour ranger, retrouver, prêter et vendre entre amis ce qu'on possède. Ce document fixe les technologies retenues pour le développement et la raison de chaque choix, dans l'ordre où elles ont été décidées.

Mise à jour du 15 septembre 2026 : le front passe d'une PWA Next.js à une application mobile React Native / Expo. Le back-end, la base de données et Docker ne changent pas. Les couches touchées par ricochet (authentification, notifications, hors ligne, paiement) sont signalées plus bas.

Mise à jour du 18 septembre 2026 : l'authentification, le hors ligne et l'organisation du code passent en « Décidé », conformément à PENDERIE_QUESTIONS_VALIDATION.md. Le scan, la distribution de l'app et les tests restent ouverts.

Comment les briques se parlent

L'application installée sur le téléphone appelle directement l'API Symfony, en joignant un jeton JWT à chaque requête. Il n'y a plus de serveur front intermédiaire. Seule l'API accède aux données, aux photos et aux services externes.

Les décisions et leurs raisons

Pour chaque couche : ce qui est retenu, pourquoi, ce qui a été écarté, et une phrase prête pour la présentation.

Symfony 7.4 LTS avec API Platform

7.4 LTSSortie nov. 2025Bugs jusqu'à nov. 2028Sécurité jusqu'à nov. 2029
8.0Sortie nov. 2025Plus maintenue depuis juil. 2026PHP 8.4 minimum
8.1Sortie mai 2026Fin de support janv. 2027PHP 8.4 minimum

Pourquoi

  • 7.4 et 8.0 sont sorties le même jour avec les mêmes fonctionnalités : la 8.0 retire seulement le code déprécié.
  • La 8.1 ne sera plus maintenue en janvier 2027, en plein développement. La 7.4 ne demande aucune montée de version avant la fin du projet.
  • Penderie gère des paiements, des adresses et un dressing privé : des correctifs de sécurité sont garantis jusqu'en 2029.
  • API Platform déclare la compatibilité ^7.4 || ^8.0 : aucune porte fermée.
  • Sans code déprécié en 7.4, le passage à Symfony 8 reste simple. C'est la voie de migration officielle.

Écarté

  • Symfony 8.1 : quelques nouveautés, contre deux montées de version à prévoir pendant le projet.
Nous avons choisi Symfony 7.4 LTS : mêmes fonctionnalités que Symfony 8.0, compatible avec API Platform, mais supportée jusqu'en 2029 contre quelques mois pour la 8.x. Et en évitant le code déprécié, le passage à Symfony 8 restera simple.

Sous Docker, prendre l'image PHP 8.4 : la 7.4 la supporte, et la migration vers Symfony 8 en sera facilitée. Confirmer la version stable d'API Platform au moment du composer require (la v5 est en bêta).

Front-endDécidé

React Native avec Expo, TypeScript et NativeWind

exporeact-nativeexpo-routertypescriptnativewind@tanstack/react-query

Pourquoi

  • Le module laisse le front libre entre Twig et une techno front. La maquette a été dessinée au format téléphone du premier écran au dernier : une application mobile la restitue telle quelle, sans réinterprétation.
  • Les fonctions du téléphone sont au cœur du produit : appareil photo, scan, galerie, notifications. En natif ce sont des API de première classe ; dans un navigateur elles dépendent du moteur, et Safari sur iOS est le maillon faible.
  • Expo évite la configuration Xcode / Android Studio : npx expo start et l'app tourne sur un vrai téléphone via un QR code. EAS Build produit les binaires dans le cloud, sans Mac.
  • expo-router reprend le routage par fichiers de Next.js et fournit une barre d'onglets native — exactement la navigation à cinq onglets de la maquette.
  • TypeScript est conservé : un champ renommé côté Symfony casse la compilation, pas l'écran de l'utilisateur.
  • NativeWind fait fonctionner les classes Tailwind en React Native : on garde les jetons du design system v2 (échelle 4 pt, rayons 8/12/16/24, couleurs de charte) et la justification déjà préparée pour Tailwind.
  • React Native, c'est React : composants, état, hooks identiques. Seules les balises changent (View et Text au lieu de div et p).

Écarté

  • PWA Next.js (choix précédent, abandonné le 15/09) : installable sans store, mais notifications push bancales sur iPhone, accès caméra tributaire du navigateur, et sensation de site web pour un produit qui vit dans la poche.
  • Twig : pages rendues par le serveur, peu adapté aux parcours en étapes de la maquette.
  • Flutter : excellent, mais impose d'apprendre Dart en plus de PHP et TypeScript.
  • Natif pur (Swift et Kotlin) : deux bases de code à tenir, hors budget du module.

Conséquence à acter : le livrable passe de web app à application mobile. À faire valider par l'encadrant.

Le front est une application mobile React Native avec Expo, en TypeScript. La maquette est pensée pour le téléphone, et le scan comme l'appareil photo deviennent des fonctions natives plutôt que des API de navigateur. Expo permet de faire tourner l'app sur n'importe quel téléphone avec un QR code, sans passer par les stores pour la démonstration.
Base de donnéesDécidé

PostgreSQL

doctrine/ormunaccentpg_trgmJSONB

Pourquoi

  • La recherche. Le cadrage demande de « retrouver un objet en quelques secondes ». Avec unaccent et pg_trgm, « etagere » trouve « Étagère » et « perseuse » trouve « Perceuse Bosch », sans moteur de recherche externe.
  • Le scan. Les informations récupérées changent selon l'objet (taille et matière pour un vêtement, référence pour un outil). JSONB les stocke et permet de les interroger avec des index.
  • L'écosystème. La distribution API Platform et le template Symfony Docker utilisent PostgreSQL par défaut : la documentation s'applique telle quelle.

Écarté

  • MySQL : parfaitement viable avec Doctrine, mais pas de recherche tolérante aux fautes sans outil externe, et un JSON moins pratique à indexer.

L'arborescence Logement › Pièce › Rangement › Carton fonctionne dans les deux (requêtes récursives) : ce point ne départage pas.

Nous avons choisi PostgreSQL, la base recommandée par API Platform. Sa recherche insensible aux accents et tolérante aux fautes répond à notre objectif de retrouver un objet en quelques secondes, et le type JSONB stocke les informations variables issues du scan.
EnvironnementDécidé

Docker Compose pour tout l'environnement

Pourquoi

  • Chaque service tourne dans son conteneur : PHP 8.4, PostgreSQL, MinIO, Mailpit. La version de PHP se choisit dans l'image, pas sur le poste.
  • Toute personne qui clone le projet le lance avec une seule commande, dans le même état.
  • Symfony génère déjà un compose.yaml : on le complète au lieu de partir de zéro.

Écarté

  • Installation locale (XAMPP…) : versions figées par le poste, environnement différent d'une machine à l'autre.
AuthentificationDécidé

Jetons JWT, rafraîchissement rangé dans le coffre du téléphone

lexik/jwt-authentication-bundlegesdinet/jwt-refresh-token-bundleexpo-secure-storenelmio/cors-bundle

Pourquoi

  • L'API ne change pas : Lexik reste la solution d'authentification décrite par la documentation d'API Platform, et délivre les mêmes jetons.
  • Le cookie HttpOnly n'a plus de sens : il n'y a ni navigateur ni serveur front intermédiaire. L'application envoie elle-même un en-tête Authorization: Bearer.
  • expo-secure-store range le jeton de rafraîchissement dans le Keychain d'iOS ou le Keystore d'Android : chiffré par le système, lié à notre application, et protégé par le code de déverrouillage. C'est plus sûr que le cookie qu'on visait côté web.
  • Le jeton d'accès (15 minutes) reste en mémoire vive et n'est jamais écrit sur le disque : fermer l'app suffit à l'effacer.
  • Sans état côté serveur : l'API ne garde pas de session, conformément à une architecture REST.
  • L'app appelant l'API directement, CORS doit être configuré (nelmio/cors) — c'était justement ce que le serveur Next.js masquait.

Écarté

  • AsyncStorage : stockage en clair dans le dossier de l'app, lisible sur un téléphone débridé ou dans une sauvegarde.
  • Cookies HttpOnly : impossibles sans navigateur, c'était la réponse à un problème (le XSS) qui ne se pose plus de la même façon.
  • Sessions Symfony : supposent des cookies et un navigateur, inadaptées à une app native.
L'authentification repose sur des jetons JWT délivrés par LexikJWTAuthenticationBundle. Le jeton d'accès, court, reste en mémoire ; le jeton de rafraîchissement est rangé par expo-secure-store dans le coffre-fort du système — Keychain sur iOS, Keystore sur Android — donc chiffré par le téléphone et réservé à notre application.
PhotosDécidé

Stockage compatible S3, photos servies par URL signées

vich/uploader-bundleleague/flysystem-bundleliip/imagine-bundleminioexpo-image-pickerexpo-cameraexpo-image-manipulator

Pourquoi

  • Confidentialité. Le dressing est privé par défaut : les photos ne sont jamais publiques. L'API génère des URL signées à durée limitée, et seulement pour qui a le droit de les voir (propriétaire, ami avec qui l'objet est partagé).
  • Portabilité. Flysystem isole le code du stockage : MinIO en développement, n'importe quel fournisseur S3 en production (AWS, Scaleway, Cloudflare R2…), sans changer une ligne.
  • Performance. LiipImagine produit une miniature pour les listes et une version moyenne pour les fiches, plutôt qu'une photo de téléphone de 4 Mo dans chaque carte.
  • La photo est centrale dans la maquette, c'est le principe UX « la photo d'abord ».
  • Côté app, expo-image-picker et expo-camera donnent l'accès à la pellicule et à l'appareil photo sans bidouille de navigateur, et expo-image-manipulator redimensionne et compresse la photo avant l'envoi : on ne téléverse plus 4 Mo pour afficher une vignette, ce qui économise le forfait de l'utilisateur.

Écarté

  • Disque du serveur : photos perdues avec le conteneur si le volume est mal configuré, et droits d'accès à coder soi-même.
Les photos sont stockées dans un espace compatible S3 et servies par des URL signées à durée limitée : une photo de dressing privé n'est jamais accessible publiquement.
NotificationsDécidé

Notifications push et e-mails, envoyés en tâche de fond

expo-notificationssymfony/mailersymfony/messengertwigmailpit

Pourquoi

  • Le push devient simple en natif. expo-notifications gère la demande d'autorisation et le jeton de l'appareil, et le service de push d'Expo relaie vers APNs (iOS) et FCM (Android) sans compte payant ni serveur dédié. C'est le gain le plus visible du passage au natif : c'était précisément le point faible de la PWA sur iPhone.
  • Le push porte l'urgent : demande de prêt, prêt accepté, rappel de retour, objet vendu. Ce sont des événements où la minute compte et où personne ne va relever ses mails.
  • L'e-mail porte ce qui doit laisser une trace, et atteint aussi celui qui a refusé les notifications : inscription, réinitialisation du mot de passe, reçu de vente, récapitulatif.
  • Messenger envoie les deux de façon asynchrone : l'utilisateur voit « Objet prêté ! » sans attendre le réseau.
  • Twig met en page les e-mails et Mailpit les intercepte en développement : aucun message ne part vers une vraie boîte pendant les tests.

Écarté

  • Push web (VAPID) : c'était l'option en PWA, avec un support iOS conditionné à l'installation sur l'écran d'accueil. Sans objet désormais.
  • FCM en direct : Expo l'utilise déjà par-dessous ; l'appeler à la main n'ajouterait que de la configuration.
  • Push seul, sans e-mail : un utilisateur qui refuse les notifications ne recevrait plus rien, pas même un mot de passe oublié.

À prévoir : une table DeviceToken (un appareil = un jeton, plusieurs par utilisateur) et un réglage par type de notification dans le compte. En production, un service d'envoi d'e-mails (Brevo, Mailjet…) pour ne pas finir en spam.

Les notifications sont doubles : en push via expo-notifications pour ce qui est urgent — une demande de prêt, un rappel de retour — et par e-mail pour ce qui doit laisser une trace. Les deux partent de façon asynchrone via Symfony Messenger. C'est exactement ce que la version web ne permettait pas de faire correctement sur iPhone.
Hors ligneDécidé

Consultation hors ligne de l'inventaire déjà chargé

NiveauCe que ça faitCoût
0 · RienPas de réseau = écran d'erreurNul
1 · Écran hors ligneL'app s'ouvre et affiche « Pas de connexion » à ses couleursFaible · inclus
2 · ConsultationVoir ses objets et leur emplacement sans réseau (au fond du garage)Retenu
3 · CompletAjouter et modifier hors ligne, synchronisation au retour du réseauÉlevé · exclu

Pourquoi

  • Le cas d'usage est réel : on cherche un objet au fond d'un garage, d'une cave ou d'un grenier, là où le réseau ne passe pas. C'est même le moment où l'app sert le plus.
  • Le niveau 2 était écarté en PWA parce qu'il coûtait cher à construire ; en natif il est presque offert : @tanstack/react-query et son module de persistance écrivent le cache des requêtes sur le téléphone.
  • Les fiches, emplacements et listes déjà consultés restent lisibles sans réseau ; les photos suivent via le cache d'images.
  • L'écriture reste bloquée : prêter, vendre, payer, partager engagent quelqu'un d'autre et demandent le réseau. Un bandeau « Hors connexion » l'annonce et désactive les boutons concernés.
  • Le dressing étant privé, le cache est vidé à la déconnexion et disparaît avec la désinstallation de l'app.

Écarté

  • Niveau 3 : file d'actions à rejouer, conflits, idempotence des requêtes — un projet à lui seul.
  • Niveau 1 seul : c'était le compromis imposé par la PWA, il n'a plus de raison d'être.
Hors connexion, l'application reste consultable : le cache des requêtes est persisté sur le téléphone, donc on retrouve un objet et son emplacement même au fond d'une cave. Les actions qui engagent quelqu'un d'autre — prêter, vendre, payer — demandent le réseau et sont désactivées : nous n'avons volontairement pas fait de synchronisation, pour ne pas avoir à gérer des conflits.
PaiementImposé

Stripe

Ce que ça implique

  • La vente se fait entre amis : l'argent doit arriver au vendeur, pas à la plateforme. Cela correspond à Stripe Connect (un compte Stripe par vendeur), pas à un paiement simple.
  • Les remboursements et litiges sont gérés par Stripe, ce qui répond au souhait du cadrage de ne pas les traiter à la main.
  • Tout le développement se fait en mode test Stripe : aucune vraie carte.
  • En natif, Stripe passe par @stripe/stripe-react-native et sa PaymentSheet : la saisie de carte est une feuille native, Apple Pay et Google Pay compris, et les numéros ne traversent jamais notre code.

À vérifier

  • Connect est-il attendu, ou un paiement simple en mode test suffit-il ?
  • Le cadrage et Asana mentionnent encore MangoPay (sections 14, 15 et validation client) : à renommer.
  • Règles des stores : Apple et Google imposent leur achat intégré pour le contenu numérique, mais exemptent les biens et services physiques entre personnes (cas des places de marché). Vendre un vêtement à un ami relève de cette exemption : Stripe est donc autorisé. À savoir expliquer à l'oral, c'est la question qu'on nous posera.

Doc à reprendre

Accessibilité : RGAA → RAAM

Le RGAA évalue des pages web ; il ne s'applique pas à une application mobile. Le référentiel équivalent est le RAAM (référentiel d'évaluation de l'accessibilité des applications mobiles), adossé aux mêmes critères WCAG. En pratique : accessibilityLabel et accessibilityRole à la place des attributs ARIA, zones tactiles de 44 pt, respect de la taille de police du système, et tests avec VoiceOver et TalkBack plutôt qu'avec NVDA. PENDERIE_RGAA.md est à reprendre sur cette base.

Plus tard

Tests et intégration continue

L'organisation du code est décidée : un seul dépôt, avec /api (Symfony) et /app (Expo) et un seul docker-compose. Une fonctionnalité qui touche l'API et l'app tient dans une seule PR, et le jury n'a qu'un lien. Restent à définir au démarrage du dépôt : les tests automatisés et l'intégration continue.
